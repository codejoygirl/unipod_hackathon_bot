# Taste — Product & UX
- Prefers zero-friction UX: no sign-in/sign-up wall and no mandatory selection or gating step before using the core feature. Wants the app to open straight into the main experience (e.g. removing the "choose a community before you can ask" gate, and dropping login/register in favor of an auto-started session). Insists on this — will re-report a remaining gate ("still requiring the community to start talking with the bot, please fix") rather than accept it. Confidence: 0.7
- Cares that the product's core answers come from a real model/service end-to-end rather than stubs or mocks, and will ask whether a backend (e.g. OpenAI) is genuinely wired in ("should we use openai so that we have real answers"). Expects mock/placeholder components to be called out and replaced once they affect answer quality. Confidence: 0.5
- Treats ChatGPT as the reference experience for chat features: a single open composer, persisted conversation history with a sidebar of past threads, and follow-up questions that carry earlier turns as context. States this explicitly and expects history to be genuinely stored, not ephemeral ("make a sidebar like chatgpt with history of conversations and they should [be] stored"). Confidence: 0.7
- Favors a clean, soft visual style for chat surfaces — both member and assistant/AI message blocks, not just one: low-contrast light-grey bubbles with generous rounding rather than sharp or high-contrast blocks, and treats the untended default as "bad" until it's polished (asked for the user bubble to be "grey light and rounder something clean", then followed up to fix the AI answer block too: "the current one ui is bad make something nice"). Confidence: 0.55
- Wants lively animated feedback while the assistant is responding/thinking instead of a plain loading affordance (asked to replace the typing dots/spinner with an animated "thinking orb" effect and was happy to pull in a third-party package for it). Confidence: 0.5
- Prefers the assistant's reply rendered as plain borderless text with no bubble/container/border — transcript-style rather than a floating card — while their own member messages may keep a soft surface. Repeats the request until it's done, even after a border/bubble was added (asked to "remove those border and container, no container around the message", then again "remove those border and container ... just clean"). Confidence: 0.6
- Prefers a flat, chrome-free layout with no separator chrome: wants the hairline dividers/borders (e.g. `border-rule` lines on the sidebar, headers, composer and around messages) stripped out, treating them as visual clutter in favor of separating regions by background/whitespace alone. Confidence: 0.5
- Prefers compact, small-footprint UI controls and treats oversized ones as a defect to fix: asks for elements to be scaled down ("make those suggestions small seems they are big") rather than accepting a large block/button treatment. Confidence: 0.45
- Prefers icon-plus-label pairing on interactive elements — a small icon next to the text on suggestion/quick-action chips — rather than bare text-only labels. Confidence: 0.45
- In light mode wants the chat sidebar/rail to sit on plain white (an elevated/raised surface) instead of a sunk tint, and expects the surrounding active/hover row colors to be flipped so they stay visible against it. Confidence: 0.4
- When a strictness/safety guardrail stands between the product and a usable answer, prefers to disable or bypass it to unblock the core feature rather than keep the strict behavior ("just remove whatever is blocking to have response") — accepts the tradeoff for a demo/hackathon, provided the strict posture can be turned back on. Confidence: 0.5
- Prefers the bot's answers to be summarized/brief — the key facts only — rather than dumping the full source content ("give summarized answers not full content we want important information"). Wants the signal (what, when, who, deadlines) without preamble or filler. Confidence: 0.6
- Wants external links and resources rendered as clickable and opened in a new tab rather than shown as plain text. Confidence: 0.5
- Prefers supporting/secondary UI (e.g. the sources/evidence list) rendered in neutral tones instead of accent colors, keeping the accent reserved for the answer state and primary calls to action — asks for this explicitly ("use neutral color"). Confidence: 0.5
- Wants the sources/citations surfaced with a deliberate, better-looking presentation rather than the default raw treatment ("just make a better ui for sources"), including recognizable origin marks per source — supplied the WhatsApp brand SVG for chat-sourced citations. Confidence: 0.45
- Prefers progressive disclosure for secondary content: wants supporting material collapsed into small, tap-to-expand affordances (evidence/sources as small "pills" that reveal full content on tap, like dropdowns) instead of rendered inline, so the primary content — the bot's answer/first message — stays visible without scrolling or being buried. Confidence: 0.55
- Cares that data the end user isn't meant to see never surfaces in the UI, and will ask the agent to proactively hunt for and fix such leaks (e.g. other members' phone numbers leaking into rendered citations) rather than only fixing cases he has already spotted. Confidence: 0.4
- Prefers interactive/labelled elements to carry human-readable words rather than opaque bare identifiers — treats a lone ID ("am just seeing E1") as a defect and expects the label itself to identify the item (e.g. showing the source name alongside the evidence id). Confidence: 0.5
- Uses Lovable as the reference for landing/marketing page polish, wanting a soft, richly-lit background rather than a flat fill, expressed in the project's own palette rather than copied verbatim ("background should be nice like that of the lovable"). Confidence: 0.5
- Wants the landing/marketing surface to feel alive rather than statically decorated: asks for animated elements to be wired in as the actual background and hero mark (e.g. an animated gradient background component supplied as a snippet, plus the animated AI orb/avatar), and pairs that with the project's own mascot image. Confidence: 0.5
- Expects the app's real project assets to be used in the UI (e.g. pointing at the bot image already in `public/`) rather than placeholder or stock imagery or text stand-ins — asks for the actual brand asset. For the brand lockup he wants the logo image and the "Zak" wordmark together (mark first, then the word), not a text-only wordmark. Confidence: 0.5
- Wants landing/marketing copy grounded in the product's own real data rather than generic descriptions of how it works — asks for the text to be rewritten "based on the export chat", i.e. concrete figures and the recurring questions drawn from the actual corpus, so the pitch reflects the real cohort and problem. Confidence: 0.5
- Prefers the core experience embedded directly on the landing page as the primary call to action — wants a working chat input (reusing the app's composer) so a visitor can ask a question and land in the answer, rather than marketing copy and a start button alone. Confidence: 0.5
- Prefers sparse, low-copy surfaces and treats multi-line text blocks as clutter — asks for a view to "look clean, too much text" and is happy for entire text elements (kicker labels, long explanatory paragraphs, secondary "prefer the full view?" link lines) to be deleted down to a single headline plus one line of supporting copy, keeping focus on the interactive element. Confidence: 0.55
- Expects a visual change to be applied everywhere the element appears, not only on the screen being discussed — when giving a branding/UI instruction he explicitly names the other surfaces ("and also in conversation"), so shared chrome (logo/brand lockup, header, composer) should be implemented once in a shared component that all surfaces use. Confidence: 0.45
